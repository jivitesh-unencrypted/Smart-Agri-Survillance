# Smart Agri Surveillance — v2 (React + FastAPI)

A locally-hosted AI surveillance / camera management system. This is a
complete architectural migration of the original Streamlit prototype
to a modern full-stack app: **React + Vite + Tailwind** on the
frontend, **FastAPI + SQLAlchemy + SQLite** on the backend, with
**YOLO/OpenCV local inference** and **WebSocket** real-time updates.

100% local. No paid APIs, no cloud AI, no cloud storage, no
artificial request/frame/detection limits — performance is bounded
only by your hardware.

---

## 1. Prerequisites

- **Python 3.10–3.12** (3.13 may not yet have prebuilt wheels for
  `torch`/`ultralytics` on Windows — 3.11 is the safest choice)
- **Node.js 18+** and npm
- A webcam, USB camera, or an RTSP/IP camera on your network
- Windows 10/11 (commands below are Windows-native; the app also runs
  fine on macOS/Linux with the obvious `venv\Scripts\activate` →
  `source venv/bin/activate` substitution)

## 3. Model setup

Your original `models/yolov8n.pt` was copied as-is to
`backend/models/yolov8n.pt` — nothing about the model, its classes,
or its weights was changed. The path is configurable via
`backend/.env` → `MODEL_PATH` if you want to point at a different
`.pt` file (e.g. a custom-trained model) later.

## 4. Backend setup (Windows)

```bat
cd backend
setup.bat
```

`setup.bat` creates a virtual environment, installs
`requirements.txt`, and copies `.env.example` to `.env` if you don't
already have one. Open `backend\.env` and, at minimum, change:

```
JWT_SECRET_KEY=change-this-to-a-random-secret-key
```

Then start the API:

```bat
start.bat
```

which runs `uvicorn app.main:app --reload --host 0.0.0.0 --port 8000`.
On first startup the app creates `database/app.db`, all tables, and a
default settings row — all automatically. There is no bootstrap admin
account: the app uses **open self-registration** (see section 4a
below), so the first account you create on the login page's "Create
account" tab is how you get in.

API docs (auto-generated by FastAPI): **http://localhost:8000/docs**

## 4a. Accounts — self-registration, no admin approval

Anyone who can reach the login page can create their own account via
the **Create Account** tab and is signed in immediately — there is no
separate admin role, no approval step, and no invite system. Every
account has equal access to the full app. This is intentional for a
single trusted local/LAN deployment; if you expose this beyond a
trusted network, be aware that open registration means anyone who can
reach the URL can get an account.

## 5. Frontend setup (Windows)

In a second terminal:

```bat
cd frontend
setup.bat
start.bat
```

This runs `npm install` then `npm run dev`. Open
**http://localhost:5173** and create your first account from the
**Create Account** tab on the login page.

If your backend runs on a different host/port, edit
`frontend/.env` (`VITE_API_BASE_URL`, `VITE_WS_URL`) before starting.

## 6. Camera configuration

From the **Cameras** page:
- **Local Webcam** — pick a device index (0 is usually the built-in
  or first USB webcam).
- **RTSP / IP / HTTP-MJPEG** — enter the stream URL
  (e.g. `rtsp://192.168.1.64:554/stream1`) plus optional
  username/password. Credentials are never returned to the frontend
  once saved, and are stored either as an obfuscated local token or
  as a reference to an environment variable (recommended for
  anything beyond a home LAN — check "store as environment variable"
  and put the value in `backend/.env`).

Use **Test** to verify a camera opens and returns a frame before
starting it, and **Start/Stop** to control streaming per camera —
either from the Cameras page or from Live Monitoring.

## 7. Database setup

Nothing manual is required — SQLite tables are created automatically
on first backend startup (`init_db()` in `app/core/database.py`).
The file lives at `backend/database/app.db`. To reset everything,
stop the backend and delete that file (and
`backend/database/.camera_key` if you also want saved camera
passwords to be discarded) — it will be recreated on next startup.

## 8. Running the application

1. `backend\start.bat` (leave running)
2. `frontend\start.bat` (leave running, in a second terminal)
3. Open http://localhost:5173, log in, add a camera, click **Start**
   on the Cameras or Live Monitoring page.

## 9. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| `pip install` fails on `torch`/`ultralytics` | Use Python 3.11 (not 3.13); on some Windows setups you may need the CPU-only torch wheel: `pip install torch --index-url https://download.pytorch.org/whl/cpu` before `pip install -r requirements.txt` |
| Webcam won't open / "Unable to open camera stream" | Close any other app using the camera (Zoom, Teams, other browser tabs); try a different device index; check Windows camera privacy permissions |
| RTSP camera times out | Confirm the URL works in VLC first; check firewall; some cameras require the substream URL, not the main stream, for reasonable latency |
| Frontend shows "Could not reach the backend" | Confirm `start.bat` is running in `backend/` and `VITE_API_BASE_URL` in `frontend/.env` matches its host/port |
| WebSocket shows "Disconnected" | Same as above — the WS URL (`VITE_WS_URL`) must point at the running backend; also check no proxy/firewall is blocking `ws://` |
| Live feed loads but never shows boxes | Check Settings → Detection thresholds aren't too high; check `/docs` → `GET /api/system/status` to confirm `model_loaded: true` |
| 401 errors / constantly logged out | `JWT_SECRET_KEY` in `.env` must stay constant across restarts — don't regenerate it on every launch |
| Model fails to load | Check `backend/models/yolov8n.pt` exists and `ultralytics`/`torch` installed successfully; see the backend console log at startup for the exact error |

## 10. Production / local-network usage

This is designed for a trusted local network (home, farm, small
office), not public internet exposure:

- Change `JWT_SECRET_KEY` before
  relying on this beyond your own machine.
- To reach the app from other devices on your LAN, start the backend
  with `--host 0.0.0.0` (already the default in `start.bat`), find
  your machine's LAN IP (`ipconfig`), and set `frontend/.env`'s
  `VITE_API_BASE_URL`/`VITE_WS_URL` to `http://<your-lan-ip>:8000`
  and `ws://<your-lan-ip>:8000/ws` respectively, then rebuild
  (`npm run build`) or restart `npm run dev` with `--host`.
- The `/api/cameras/{id}/stream` MJPEG endpoint is intentionally left
  without a bearer-token check (browsers can't attach auth headers to
  an `<img>` tag) — treat it like any other unauthenticated stream on
  your network and restrict it at your router/firewall if needed
  beyond a trusted LAN.
- For a real production deployment, put this behind a reverse proxy
  (e.g. nginx) with HTTPS/WSS, and run the frontend as a static build
  (`npm run build` → serve `frontend/dist/`) rather than the Vite dev
  server.

## A. What changed — old stack → new stack

| Layer | Old (Streamlit) | New |
|---|---|---|
| UI | Streamlit pages (`views/*.py`), session_state | React 18 + Vite + Tailwind CSS, React Router |
| UI refresh | `st.rerun()` / polling loops | WebSocket push (`/ws`) + React state |
| Backend | None (UI and logic were the same process) | FastAPI + Uvicorn, clean REST API under `/api/*` |
| Video I/O | `streamlit-webrtc`, in-process `cv2.VideoCapture` | Background per-camera thread (`CameraStreamWorker`) + MJPEG-over-HTTP for video, WebSocket for metadata |
| Detection | Ultralytics YOLO, per-frame, in the Streamlit process | Same Ultralytics YOLO model (your existing `.pt` weights), loaded once process-wide, run at a configurable interval with frame-skipping |
| Detection storage | CSV files (`data/detections.csv`, etc.) via `utils/file_utils.py` | SQLite (`detections` table) via SQLAlchemy, with **event-based** rows instead of one row per frame |
| Camera config | JSON/session-state via `utils/camera_manager.py` | SQLite `cameras` table via SQLAlchemy, CRUD REST API |
| Auth | None | JWT-based login (bcrypt-hashed passwords), open multi-user self-registration, no admin approval step |
| Alerts | In-memory / session-state banners | SQLite `alerts` table, REST API, WebSocket push, acknowledge/resolve workflow |
| Snapshots | Local files referenced from CSV | Local files under `storage/snapshots/YYYY-MM-DD/`, served via `/storage/*`, referenced from the `detections` table |
| Analytics | Recomputed from CSV in `views/video_analysis.py`/dashboard | SQL aggregation queries in `analytics_service.py`, charted with Recharts |

## D. Features preserved

- Live camera feed (webcam, USB, RTSP, IP/HTTP-MJPEG)
- Real-time YOLO object detection with bounding boxes, labels, confidence
- Person / animal / vehicle detection categories (same class mapping
  as the original `CATEGORIES` dict in `config.py`)
- Detection count, FPS, timestamp — now pushed live via WebSocket
  instead of a Streamlit rerun loop
- Detection history / logs, with filtering (source, category,
  severity, camera, date, text search) and CSV export
- Automatic snapshots on detection events
- Warning/alert generation with the same severity mapping (Human →
  critical, Animals → warning, Vehicles → info, Others → normal)
- Camera management (add/edit/delete/enable/disable, connection
  testing, credential handling with the same env:/obfuscation scheme)
- Camera status/health (online/offline, last FPS, latency, last seen)
- Analytics (daily/weekly/monthly trends, by-category, by-camera,
  peak hours) — same underlying questions the original video-analysis
  view answered, now backed by SQL instead of recomputing from CSV
- Settings for confidence threshold, IoU threshold, and detection
  behavior
- Dashboard summarizing system/camera/detection/alert status

## E. Features improved

- **No duplicate per-frame records.** The original risk of writing a
  DB/CSV row per frame is solved with true event-based grouping
  (`CameraEventTracker` in `detection_service.py`): a continuously
  detected object is one row, extended in place, until a configurable
  cooldown elapses.
- **True real-time updates** via WebSocket instead of Streamlit
  reruns/polling — detections, alerts, FPS, and camera status push to
  every connected client instantly.
- **Configurable, efficient inference pipeline** — inference interval
  and frame-skip are both adjustable from Settings without touching
  code, so a slower machine can trade detection latency for
  responsiveness.
- **Multi-camera, concurrent** — each camera runs in its own
  background thread; the original Streamlit app effectively handled
  one active stream at a time in the UI thread.
- **Real authentication** — JWT + bcrypt, where the original had none.
- **Structured, queryable storage** — SQLite + indexes on
  `timestamp`/`camera_id`/`detection_type` replace flat CSV files, so
  filtering, pagination, and aggregation are fast even with a large
  history.
- **Automatic interactive API docs** at `/docs` (FastAPI/Swagger),
  useful for testing or integrating other tools.
- **Graceful degradation** — camera disconnects show a clear
  "reconnecting" placeholder in the video feed and auto-retry, rather
  than an error page; a missing/broken model is reported via
  `/api/system/status` instead of crashing the app.

## F. Remaining issues / what could not be fully executed here

Built in a sandboxed environment **without internet/package-registry
access**, so the following could not be executed end-to-end in this
session — they need to be run on your machine per section 4/5/8:

- `pip install -r requirements.txt` (FastAPI, SQLAlchemy, Ultralytics,
  torch, python-jose, passlib, etc.) — none of these packages could be
  downloaded here, so the backend was never actually booted with
  `uvicorn` in this sandbox.
- `npm install` — React, Vite, Tailwind, Recharts, and lucide-react
  could not be fetched, so the frontend was never bundled or opened in
  a browser here.
- Live YOLO inference, actual camera capture, and a live WebSocket
  round-trip in a browser were consequently **not run** in this
  session — I could not verify FPS numbers, real detection accuracy,
  or the exact visual layout on a real screen.
- Recording to `storage/recordings/` is scaffolded (the folder exists
  and is referenced) but no recording feature was implemented — the
  original Streamlit app didn't have one either, so nothing was lost,
  but if you want video recording (not just snapshots) that's new work.
- Scheduled cleanup of old snapshots (`max_snapshot_age_days` in
  Settings) is stored but **not yet enforced** by a background job —
  it's there for a future cron/scheduled task; nothing currently
  deletes old snapshots automatically.
- WebRTC was not used for the live video path (MJPEG-over-HTTP was
  used instead) — see the note in section 10 and in `api/cameras.py`;
  this is a deliberate simplification, not an oversight, but it's a
  real behavior change worth knowing about (no peer-to-peer
  negotiation, no adaptive bitrate — just a straightforward JPEG push
  over HTTP).
